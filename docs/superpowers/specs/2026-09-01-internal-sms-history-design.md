# 내부 생산 문자 발송내역 화면 설계

## 1. 목표

첫 화면의 `현장 작업자`·`영업 관리` 카드 아래에 `문자 발송내역 확인하기` 진입 버튼을 추가한다. 전용 화면에서는 이번에 도입한 내부 생산 자동문자만 간부와 팀원으로 나누어 발송 시각, 수신자, 발송 상태, 제목과 본문까지 확인할 수 있어야 한다.

## 2. 승인된 접근 범위

- 별도 로그인이나 인증 없이 조회할 수 있다.
- 전체 전화번호는 노출하지 않고 기존 발송 로그의 마스킹 번호만 표시한다.
- `internal_` 접두사가 붙은 내부 생산 문자만 조회한다.
- 고객 안내문자와 기존 영업담당자 위험 알림은 조회하지 않는다.
- 간부는 이시아·최우석·이정섭·김보수·박상규·정영호 담당자이다.
- 팀원은 강종효·카우사르·나타왓·마카라·백승정·까지이다.
- 실제 문자 발송 규칙, 수신자, 평일 일정과 중복 방지 로직은 변경하지 않는다.

## 3. 데이터 설계

기존 `notification_log`에 다음 nullable 컬럼을 추가한다.

| 컬럼 | 용도 |
|------|------|
| `recipient_name` | 발송 당시 수신자 이름 |
| `message_subject` | 발송 당시 LMS 제목 |
| `message_text` | 발송 당시 문자 본문 |

스키마 보정은 기존 `ensureNotifySchema`의 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 방식으로 수행한다. 기존 행을 갱신하거나 다시 쓰지 않는다. 이전 기록에서 새 컬럼이 비어 있으면 화면에 `내용 저장 전 기록`으로 표시한다.

`sendAdminLms`는 선택적 `recipientName`을 받아 제목·본문과 함께 발송 로그에 저장한다. 내부 생산 문자 발송 경로만 이 값을 넘긴다. 기존 고객 문자와 영업 위험 알림 호출 방식은 보존한다.

## 4. 조회 API

새 GET API `/api/internal-notifications`를 추가한다.

- 인증을 요구하지 않는다.
- `milestone LIKE 'internal_%'`인 로그만 최신순으로 반환한다.
- 기본 50건, 최대 100건으로 제한한다.
- `전체`, `간부`, `팀원` 필터를 지원한다.
- 팀원 여부는 `internal_assembly_daily` 마일스톤으로 판정하고 나머지 내부 알림은 간부로 판정한다.
- 응답에는 로그 ID, 수신자명, 구분, 마스킹 전화번호, 상태, 제목, 본문, 발송 시각만 포함한다.
- 공급자 오류 원문, 전체 전화번호, 환경변수와 인증정보는 반환하지 않는다.
- 응답은 `no-store`로 캐시하지 않는다.

상태 표시는 다음처럼 정규화한다.

- `success`: 쏠라피 발송 요청 성공
- `failed`: 발송 실패
- `dry_run`: 테스트 기록

이 화면의 성공은 통신사 최종 수신 확인이 아니라 쏠라피 API가 발송 요청을 정상 접수했다는 의미로 표시한다.

## 5. 화면 설계

### 홈 진입 버튼

- 두 역할 카드 바로 아래, 하단 문구 위에 배치한다.
- 흰색 바탕, 연한 파란 테두리, 메시지 SVG 아이콘, `문자 발송내역 확인하기` 문구와 우측 화살표를 사용한다.
- 기존 홈의 최대 폭, 표면, 그림자, hover/active 규칙을 재사용한다.
- 모바일에서는 카드와 같은 전체 폭 48px 이상 터치 영역을 보장한다.

### 발송내역 화면

- 경로: `/sms-history`
- 상단: 홈으로 돌아가기, 제목 `문자 발송내역`, 설명 `내부 생산 자동문자 발송 현황`
- 요약: 전체·성공·실패 건수
- 필터: `전체 / 간부 / 팀원`
- 목록: 수신자명, 간부·팀원 배지, 상태 배지, 마스킹 번호, KST 발송 시각, 제목
- 본문: 각 항목의 `발송 내용 보기`를 눌러 펼치고 다시 접을 수 있다.
- 상태별 색은 기존 디자인 토큰의 파랑·초록·빨강만 사용한다.
- 로딩, 빈 목록, 조회 실패와 재시도 상태를 별도로 제공한다.
- 375px, 768px, 1280px에서 읽기 쉽고 가로 스크롤이 없어야 한다.

## 6. 데이터 흐름과 오류 처리

1. 내부 문자 발송 시 쏠라피 결과와 함께 수신자·제목·본문을 `notification_log`에 append한다.
2. 발송내역 화면이 공개 조회 API를 호출한다.
3. API는 내부 문자만 제한된 개수로 조회하고 공개 가능한 필드로 변환한다.
4. 화면은 필터와 펼침 상태를 클라이언트에서 관리한다.
5. 로그 저장 실패가 실제 공정 시작·완료 처리를 실패시키지 않는 기존 불변식을 유지한다.
6. 조회 실패 시 이전 데이터를 성공으로 꾸미지 않고 오류와 재시도 버튼을 표시한다.

## 7. 검증 기준

- 홈 카드 아래 진입 버튼이 있고 `/sms-history`로 이동한다.
- 인증 토큰 없이 API와 화면이 열린다.
- 내부 생산 문자만 조회되고 고객·영업 문자는 제외된다.
- 간부/팀원 필터가 정확히 분류한다.
- 새 발송 기록은 수신자, 상태, 시각, 제목, 본문을 표시한다.
- 기존 기록의 본문이 없으면 안전한 대체 문구를 표시한다.
- 전화번호는 끝까지 마스킹된 값만 노출된다.
- 실패 상태와 쏠라피 접수 성공을 구분한다.
- 문자 발송 테스트에서는 실제 쏠라피 호출을 하지 않는다.
- 전체 회귀 테스트와 프로덕션 빌드가 통과한다.
- 실제 브라우저에서 375px, 768px, 1280px 화면과 펼침·필터·재시도 상태를 확인한다.

## 8. 위험과 되돌리기

- 사용자가 인증 없는 조회를 명시적으로 승인했으므로 문자 본문은 공개된다. 전체 전화번호와 고객 문자는 공개하지 않아 노출 범위를 제한한다.
- 컬럼 추가는 기존 데이터를 다시 쓰지 않는 additive 변경이다. 기능을 되돌릴 때 API와 UI만 제거해도 기존 발송 기능은 유지되며, 남은 nullable 컬럼은 동작에 영향을 주지 않는다.
- 기존 문자 발송 로직과 영업담당자 알림 파일은 수정하지 않는다.
